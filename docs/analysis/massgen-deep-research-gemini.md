## 執行摘要

MassGen 是由 AutoGen（現 AG2）創始人 Chi Wang 和其團隊於 2025 年推出的開源**多代理協作框架**，目標在於通過「並行學習小組」方式組合多個大語言模型（LLM），解決複雜任務。與單一智能體相比，MassGen 讓多個代理（可使用不同模型如 OpenAI GPT、Anthropic Claude、Google Gemini、xAI Grok 等）**異步並行推理**，互相觀察並以投票達成共識，提升答案質量和可靠度。

---

## 背景與定位

**來源與作者**：MassGen 為開源項目，由 Chi Wang（DeepMind 資深研究員、AutoGen/AG2 創始人）領導開發。

**發布時間與目的**：2025 上半年選為公開（GitHub 0.0.3 起步，至 2025 年 11 月發布 v0.1.12 版本）。主要用途在於研究和開發多代理協作解題框架，系統將用戶任務分派給多個 AI 代理，讓它們**並行推理**、**交換意見**，最終**自然達成共識**以產生高質量答案。

**授權**：Apache 2.0 開源，可在 Terminal、CLI、Web UI 或 API 模式下使用。

## 系統架構與模組職責

MassGen 採三層架構：**Orchestrator**（協調層）、**Agents**（代理執行層）、**Backend Abstraction**（模型後端層）。

**數據輸入**：用戶通過 CLI 或 API 提交任務描述或問題（Prompt），Orchestrator 讀取輸入並初始化交互上下文，可能加載「上下文路徑」（context paths）以供讀寫。

**預處理**：Orchestrator 解析 YAML 配置文件，配置多個 Agent，每個 Agent 可指定不同後端類型（如 OpenAI API、Claude API、LiteLLM 本地模型等）和工具（MCP 工具組、文件操作等）。若需要使用工具（如 Web 搜索或資料庫查詢），Orchestrator 通過 MCP（Model Context Protocol）整合外部工具。可在配置中啟用文件系統功能，使代理具有限制性的文件讀寫權限。

**模型架構**：MassGen 本身不訓練新模型，而是**可與多個預訓練 LLM 協作**。代理層（Agent Layer）可使用不同模型（如 GPT-5、Claude Sonnet、Gemini Pro、Grok-4 等），並可配置模型相關參數（系統提示、令牌限制等）。每個 Agent 在獨立子進程或線程中運行，通過 Backend 抽象層與實際模型互動。

**推理流程**：Orchestrator 按設置啟動多個 Agent，每個 Agent 異步同步向選定的 LLM 提交任務，運行中，代理還可立即「觀察對方最新答案並進行交流」，每次迭代，Agent 可以選擇**新增答案**或**對現有答案投票**。若有代理提交新答案，Orchestrator 通過「注入繼續（inject-and-continue）」機制將此答案注入其他代理的工作流，避免重啟整個推理並保存原始思路。

**協作共識**：Agents 進行多輪投票，直到**所有代理都完成投票**為止，票數最高的答案即為「贏家」，由該 Agent 報告為最終結果。這種**多模型並行+投票機制**不依賴強制一致，即使多數票才可接受（或設置共識閾值），實現自然收斂到最可信答案。

**後處理**：Orchestrator 收集最終答案後，可進行格式化或文件輸出，並將結果傳達用戶。MassGen 還將每輪對話和答案**保存到文件系統**中，每個 Agent 有獨立工作目錄（`workspaces/agentX`），每次提交答案都在 `snapshots/` 目錄生成快照，並將整個對話記錄於 `sessions/` 目錄。

## 核心算法與技術細節

**代理協作模式**：MassGen 的核心並非機器學習訓練，而是一種**協作推理算法**。每位 Agent 在執行時都保持獨立推理，並分享觀察結果。採用**多輪迭代投票**，每輪由所有 Agent 先後決定新增答案或對現有答案投票。當所有 Agent 都完成投票後（通常通過檢測投票完成率達到最大輪數），票數最高的答案即被選定。此流程類似「小組討論」，避免了串行推理的單一依賴。

**投票機制與注入**：MassGen 引入**投票共識檢測**，並在需要時使用「**注入繼續（inject-and-continue）**」技術加速收斂。一般情況下，每輪都讓所有代理執行任務；若有代理 A 提出新答案，其他代理在下一輪立即「看到」該新答案並更新思路，而不用重啟代理已有進度。因此，MassGen 保存了代理每一輪的中間結果快照，並將新資訊及時注入平行運算中，大幅減少運算浪費。

**後端抽象與混合**：MassGen 已整合了多種 LLM 平台和工具。Backend 抽象層統一接口，可並行使用多種模型，支持跨平台串接（如 OpenAI、Anthropic、Google、xAI 及各種本地模型如 LiteLLM、vLLM）。並行代理可分別連接不同後端，實現**跨模型協作**。此外，系統內建整合 MCP（Model Context Protocol）的能力，使代理能使用網絡搜索、資料庫、文件系統等工具。MassGen 還支持通過容器（Docker）進行複雜任務自動化，如協同控制 Claude+Gemini 環境以進行跨平台操作。

**記憶體管理**：MassGen 具有**對話與記憶管理**機制。它將每次執行的對話歷史儲存為「Turn」，而整個多代理對話保存在 `sessions/` 中。在多輪互動模式（Interactive Mode）下，可保持上下文連續，並支持**永久記憶**，最新版本已引入基於向量檢索的「記憶 MCP」模組，將對話和知識以 Markdown、向量形式跨代理共享。當上下文接近限制時，MassGen 會自動執行**漸進式上下文壓縮**，將過往對話摘要從裁剪後並妥善保存，確保不失去關鍵線索。

## 資料管理線與標注策略

MassGen 主要面向即時任務，不含傳統的訓練資料管線。因此：
- **資料來源**：輸入資料即是用戶提出的任務描述和上下文文件，系統本身無自動抓取外部訓練資料。若整合網絡工具（MCP），則可從指定 API/網站檢索資料，用戶應檢查抓取結果的合法性和準確性。
- **數據洗理與標注**：由於 MassGen 不執行監督學習，並無標注需求。若將 MassGen 輸出用於下游應用，可考慮在人類審核後增加標籤，或在訓練管線中用 MassGen 的輸出/答案做弱標籤。
- **資料平衡**：無需處理訓練資料數據不平衡問題。但在多模型協作中，不同模型可能對特定問題有不同偏好，可通過加入更多模型來平衡觀點。
- **隱私與合規**：MassGen 運行需管理 API 密鑰和機密資訊。官方文件建議將敏感文件置於**保護路徑**（Protected Paths），禁止任何代理讀寫，以防外洩。另外，多代理系統更注重**資訊傳播正確**風險，若任務涉及個人或受保護資料，應嚴格限制代理的存取權限與記憶使用（可選擇在對話結束後刪除記憶或啟用臨時記憶功能）。在企業部署時，建議符合 GDPR/CCPA 等法規，並在組織內部規範好 AI 生成內容的審核與責任分工。

## 性能指標與評估方法

**成本與延遲**：MassGen 的計算資源消耗主要來自多個 LLM 的串行/並行調用。理論上，N 個代理並行最多 API 調用量是單代理的 N 倍，因此**推理成本**不可忽視。使用付費 API（如 GPT-5）時，需要估算總 token 量並適度限制輪數或換成資源成本較低的模型。**延遲**方面取決於最慢代理的響應、網絡狀況和投票輪數，可通過配置讓代理異步並行，並在投票完成後立即中止進一步運算，減少不必要的等待。**吞吐量**方面，如需同時處理多任務，可串行或並行啟動多個 MassGen 實例，但需考慮硬件和 API 並發限制。

**準確度與質量**：MassGen 無固定「準確度/公開分」指標，因任務性質多樣。然而，可針對特定任務（如答題、摘要、代碼等）進行 A/B 測試，將多代理設置與單代理 baseline 比較，評估「正確性」或「滿意度」等。官方表示**多代理協作可帶來統計上顯著提升**。評估時建議設計以下實驗：固定任務類型，執行多組實例，對每組答案質量（例如人工評分）與單代理對比。通過 ablation 分析不同代理數量或不同模型組合的效果。

## 安全性、偏見與可解釋性評估

**攻擊面**：MassGen 增加了多個代理協作的新攻擊面。例如，惡意輸入可能誘導多個代理形成錯誤決策；代理之間的資訊共享機制若未加保護，也可能被利用（如注入攻擊對其他代理）。因此，建議對代理輸入進行內容過濾（防止注入攻擊），並限制代理操作（例如只允許讀文件不允許隨意執行命令）。質量保障方面，可使用 MassGen 提供的**模擬人工審查面板**（任務完成後可檢視每輪輸出並人工介入），以避免重大錯誤。

**對抗性測試**：目前官方未有明確的對抗測試套件，但用戶可採用與 LLM 相似的對抗測試方法（如添加乾擾詞、惡意提示等）來檢驗系統魯棒性。值得注意的是，多代理系統可能在某些攻擊上**形成迴路**，若有代理在迭代中不斷給出同一錯誤答案，其他代理可能學習失敗思路。應設置警報機制（如若多輪後一致性低或代理行為異常，則停止並進行人工檢查）。

**偏見緩解**：不同模型往往帶有各自的偏見，多模型協作有時可相互校正。例如，對具社會敏感議題（多個模型如果有相似偏見），從眾效應可能使最終答案依然有問題。因此，可在配置中**混搭不同背景的模型**（例如中美大選、歐洲等不同語言訓練的模型），並監控輸出結果，或在 Orchestrator 加入去偏邏輯（例如由專業的過濾代理進行最終審查）。此外，可收集多代理輸出並使用可解釋性工具（如 LIME、SHAP）分析各代理貢獻。

## 部署與維運

**CI/CD & 版本管理**：MassGen 支持命令行及程序庫兩種使用方式，可將其納入 DevOps 流程。建議使用 Git 進行配置文件的版本管理，並利用 CI（如 GitHub Actions、Jenkins）自動執行測試任務和部署。推出新版本時，可設置測試場景自動跑 MassGen 以確保協作邏輯正常。

**滾動更新**：由於多代理長時間任務可能被中斷，需使用「session」機制保存進度。一旦系統更新，可讓 Orchestrator 讀取前次 `sessions/` 繼續執行，或啟動全新任務。更新代理模型版本時，先在開發環境進行 A/B 測試，再在正式環境漸進式推出。

**監控指標**：關鍵監控項目包括：API 調用成功率、平均推理時間、任務完成率、成本費用（USD 或運算小時）、以及內部質量指標（如代理間一致性）。可利用 Grafana + Prometheus 收集這些指標。MassGen 支持輸出多種度量（如每輪 token 消耗、投票統計）。在企業級使用時，也可整合自動異常偵測，一旦任務質量或性能指標偏離基準，就自動警告並回滾。

## 實作建議與工程路線圖

### 短期目標（0–3 個月）
- **核心架構搭建**：設計 Orchestrator 核心和 Agent 基礎架構，實現多模型並行調用。使用現有的 LLM API（如 GPT-4, Claude）作為後端。
- **配置系統**：設計 YAML/JSON 配置格式，支持指定代理、模型、投票規則等。參考 MassGen 配置範例。
- **投票與共識算法**：實作基於票數的共識機制，可預設最大輪數和共識閾值，防止無限迴圈。例如，配置 `max_new_answers_per_agent` 和 `max_new_answers_global` 上限。
- **單元測試**：針對基礎協作流程新寫測試場景，例如固定任務讓兩個代理協作，檢查投票結果是否合理。
- **本地部署**：在開發環境部署小規模本地推理，例如使用 LiteLLM 或 vLLM，以降低前期成本。

### 中期目標（3–6 個月）
- **多模型與工具整合**：新增對多家模型的支持，並整合常見工具（Web 搜索、程序執行、資料庫查詢）作為 MCP 插件。
- **監控與接入**：實作詳細接入日誌系統，記錄每輪投票和代理輸出，方便在運行時分析和調優，並實現 `logs` 命令行工具。
- **CI/CD & 部署管道**：配置自動化流程，將配置文件和程序代碼設為版本控制，並在每次提交時自動執行基本測試。
- **性能優化**：進行負載測試，調整代理並行度和超參數。利用 LiteLLM、DeepSpeed-inference 等技術加速本地推理，若進行端 API 調用，考慮批次請求和並發限制。

### 長期目標（6–12 個月）
- **增強協作策略**：研究改進共識機制，如適應性投票閾值、分層協作（例如分組討論和可彙總）。結合最新多源智能體研究成果（例如多輪自治式學習、少量訓練等）進一步改善穩定性。
- **自動化工具與 UI**：開發 Web 或臺面界面，讓非技術用戶配置和啟動多代理任務。實現即時可視化和在線編輯，參考 MassGen 的 Web UI。
- **評估與優化**：針對目標領域（如客戶、自動化報告、程序生成等）建立基準評估集，定期進行 A/B 測試，收集使用者反饋，根據結果優化代理組合策略和參數。
- **社區與知識庫**：建立內部知識庫，儲存成功案例和最佳實踐。鼓勵成員分享配置模板、文件和資料，若可能，可開源社區合作，促進框架的持續演長。
