# Phase 0.2 — History Condensing Phase 1（Sliding Window）設計規格

> 撰寫日期：2026-03-19
> 版本：v1
> 狀態：待實作
> 關聯 ROADMAP：Phase 0.2

---

## 問題描述

目前 `history_text` 是無限累積的純文字字串，每輪每個 agent 都會追加一段：

```
[AgentName]: {完整回應}\n\n
```

在長時間對話（數十輪、多 agent）後，`history_text` 會超過數萬字元，導致：

| 失效模式 | 影響 |
|---------|------|
| prompt 超過 CLI agent 的 context window 上限 | agent 拒絕執行、截斷輸入、或回傳亂碼 |
| token 成本隨對話長度線性成長 | 成本失控（若未來接 API 計費） |
| 早期對話注入 prompt 導致模型分心 | 回應品質下降，agent 無法聚焦當前問題 |

---

## 設計目標

1. **不超量**：任何時刻送給 agent 的 `history_text` 字元數不超過 `max_history_chars`
2. **保留重要上下文**：保留最近 N 輪（`MAX_TURNS`），確保 agent 讀得到完整的當前討論
3. **不切斷句子**：truncation 發生在「輪」的邊界（每個 `[AgentName]:` 區塊的開頭），不在字元中間截斷
4. **透明標示**：省略的部分加上 `[... 較早對話已省略 ...]` 標記，讓 agent 知道有歷史被移除
5. **不改 API、不改 UI**：Phase 1 純 backend 內部調整，使用者感知不變

## 實作細節

### 截斷時機

在 WS handler 每輪 `build_prompt()` 前，對 `history_text` 進行 sliding window 截斷。

截斷策略優先使用**字元數閾值**（精確、不需 parse），輔以**輪次計數**（語意完整性保護）：

1. 若 `len(history_text) <= max_history_chars`：不截斷，直接使用
2. 若超過閾值：從最舊的 `[AgentName]:` 區塊開始逐一移除，直到字元數低於閾值
3. 移除後，在最前面插入截斷標記

### 函式設計

新增 `truncate_history(history_text: str, max_chars: int) -> str`：

```python
TRUNCATION_MARKER = "[... 較早對話已省略 ...]\n\n"

def truncate_history(history_text: str, max_chars: int) -> str:
    """
    Sliding window 截斷：從最舊的 [AgentName]: 區塊移除，
    直到 history_text 字元數低於 max_chars。
    截斷後在最前面插入 TRUNCATION_MARKER。
    """
    if len(history_text) <= max_chars:
        return history_text

    # 以 \n[AgentName]: 為分界切開各輪次區塊
    import re
    # pattern 匹配「換行後跟著 [任意名稱]:」作為分割點
    segments = re.split(r'(?=\n\[[\w\s\-]+\]: )', history_text)

    # 從最舊端移除，直到符合長度
    while segments and len("".join(segments)) > max_chars:
        segments.pop(0)

    truncated = "".join(segments)
    return TRUNCATION_MARKER + truncated.lstrip("\n")
```

### 呼叫位置

在 WS handler 的每輪迴圈中，`build_prompt()` 呼叫前加入截斷：

```python
# 每輪開始前截斷
trimmed_history = truncate_history(
    history_text,
    max_chars=config.get("max_history_chars", 80000),
)
prompt = build_prompt(agent, trimmed_history, workspace_id, all_agents)
```

注意：`history_text` 本身**繼續無限累積**（保留完整記錄），截斷只影響送給 agent 的 `trimmed_history`。若未來需要持久化完整歷史，不需要額外改動。

### `MAX_TURNS` 輔助保護（可選）

若截斷後剩餘的輪次數量仍超過 `MAX_TURNS=20`，額外移除最舊的整輪（以 `[AgentName]:` 區塊計數）。此保護作為字元閾值的補充，防止大量短回應繞過字元限制。Phase 1 可先只實作字元閾值，`MAX_TURNS` 留作 Phase 2 調整。

## Config 更新

**`config.json`（全域層）：**

```json
{
  "max_history_chars": 80000
}
```

| 欄位 | 型別 | 預設值 | 說明 |
|------|------|--------|------|
| `max_history_chars` | int | 80000 | history_text 送給 agent 前的最大字元數；約 20K tokens（估算） |

不在 agent-level `config.json` 設定此值（所有 agent 共用同一份 history，個別 agent 設不同閾值沒有意義）。

## 測試計畫（TDD）

### Unit Tests（`truncate_history()`）

| 測試 | 輸入 | 預期 |
|------|------|------|
| 不超量時不截斷 | `len < max_chars` | 原字串不變，無標記 |
| 超量時從最舊移除 | 4 輪對話、`max_chars` 只容 2 輪 | 剩最新 2 輪，最前有截斷標記 |
| 截斷標記只出現一次 | 多次呼叫 | 標記不重複疊加 |
| 截斷後不切斷句子 | 長回應跨多行 | 輸出為完整 `[AgentName]:` 區塊 |
| 全部移除後空字串 | 單一超長回應 > max_chars | 回傳僅含截斷標記（或空） |
| 恰好等於閾值 | `len == max_chars` | 不截斷，原字串返回 |

### Integration Tests（WS handler）

| 測試 | 情境 | 預期 |
|------|------|------|
| 長對話 prompt 被截 | 模擬 30 輪對話後送給 agent | agent 收到的 prompt 字元數 < `max_history_chars + overhead` |
| 截斷標記在 prompt 中 | 上述情境 | prompt 含 `[... 較早對話已省略 ...]` |
| `history_text` 本身不截斷 | 同上 | `history_text` 原始物件長度 > `max_history_chars` |
| 短對話不截斷 | 3 輪對話 | prompt 無截斷標記 |

## 不在此 Phase 的範圍

- **語意壓縮**（用 LLM 摘要早期對話）：Phase 0.2 只做 sliding window，不摘要
- **Per-agent 不同閾值**：所有 agent 共用 `max_history_chars`
- **Token 計數**：使用字元數近似，不接 tokenizer API
- **持久化歷史 / 歷史查詢 UI**：Phase 5 範疇
- **`MAX_TURNS` 精確實作**：Phase 1 字元閾值已足夠，MAX_TURNS 輔助保護可延後
- **Workspace guide.md 永遠保留**：guide.md 注入在 `build_prompt()` 的 context 區（非 history 區），不受此截斷影響
