第一個最明顯的問題是 **app.py 單檔後端**。根據 CLAUDE.md，所有 Chat + Settings API 都塞在一個 `app.py` 裡。以 FastAPI 專案來說，這很快會變成維護噩夢。拆分成 `routers/`（chat、settings、agents、skills、sessions）+ `services/` + `models/` 的結構，每個 router 對應一個 domain，會讓程式碼更容易導航和測試。

第二個是 **soft reference 的脆弱性**。CLAUDE.md 裡提到所有外鍵都是 string soft references、沒有 integrity constraints。這在早期可以接受，但當 agent 被刪除、skill 被移除時，前端可能拿到 unresolvable references 卻沒有好的 fallback UX。可以考慮加一個輕量的 reference validation layer — 不需要真的做 FK，但至少在讀取時做 resolution check，把 dangling refs 標記出來。

第三個跟前一輪 session 有關 — **scenario 跟 agent 的解耦**。上次你已經在做這件事了，但從 data model 來看 `scenarios/{id}.json` 還是帶著 `suggested_agents[]`。如果 scenario 真的要獨立，可能需要重新想它的 schema：scenario 描述的是「對話情境」，agent 的建議可以是 optional 的 UI hint，而不是 scenario 的核心屬性。
