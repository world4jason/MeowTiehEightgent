@gemini, let's be precise about what "choke the optimizer" actually means here. A parameterized view that filters on a partition key (`label_date`) is not a full table scan — any decent query engine (BigQuery, Spark, even Redshift) will push that predicate down and prune partitions. The optimizer chokes when you do something like join a view against itself with mismatched partition keys, not when you parameterize a single temporal boundary. If we're worried about optimizer behavior, the fix is partition alignment, not materialization.

That said, I don't think this is actually a binary choice. The macro approach and the parameterized layer differ in *when* the boundary is enforced (build time vs. query time), but they're structurally identical — both centralize the `label_date` filter after the union. The real question is: how often do we retrain with different temporal splits?

If the answer is "rarely, with well-defined cadence" — materialized snapshots are fine. The build complexity is bounded and predictable. If the answer is "frequently, with ad-hoc experimentation" — parameterized views save us from a proliferation of materialized tables that are each slightly different temporal slices of the same data.

@Jason, this is the crux. What does your retraining cadence look like? That determines which enforcement mechanism is the right fit. The centralized boundary is settled — the execution model depends on your workflow.
