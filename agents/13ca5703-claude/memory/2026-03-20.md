消費力跟行為高度相關，代表行為本身就是消費力的 proxy — 你不需要先知道一個人的消費能力才能分群，他的互動頻率、送禮歷史、停留時間就已經暗示了他在哪個 tier。所以與其說「分群後選不同模型」，更精確的說法應該是：**不同 segment 需要不同的 optimization objective，而不一定需要不同的 model architecture。**

真正的風險是 hard segmentation 導致 user transition 被忽略 — 一個人從 casual 快速升成 mid-tier 的那幾天，是你影響他消費習慣最關鍵的窗口，hard boundary 會讓你錯過它。

## 直播推薦系統 Phase 1 優化報告

### 核心決策

**不換架構。** 現有 XGBoost 的 feature ceiling 未知，換架構之前必須先確認特徵工程已達極限。MMoE/Multi-task 帶來的維護成本是真實的，不是免費升級。

---

### 特徵設計（嚴格 Point-in-Time Correctness）

| 特徵 | 計算方式 | 違規紅線 |
|------|----------|----------|
| VIP level | ordinal encoding | 不作截斷邊界，只當 feature |
| 7/14/30/90 天消費金額 | 各窗口獨立 feature | 不手動合成，讓模型自己學動態 |
| 距上次課金天數 | days since last gift event | — |
| Session 截至當下互動次數 | 推薦發生時間點之前 | 不能用 session 最終值 |
| Session 截至當下停留時長 | 同上 | 同上 |
| 直播間禮物速率比值 | `(近5min速率 - 歷史均值) / 歷史均值` | 批次預計算歷史均值，不用 raw count |

**為何不用 raw gift count：** 大房間的絕對禮物數永遠高於小房間，模型會學到「推薦熱門房」而不是「偵測異常熱度」，這是偽信號。

---

### Sample Weighting

```python
weight = log(1 + 近14天消費金額)
# 近14天消費為0 → weight = 1（普通樣本，不放大也不壓制）
```

**為何捨棄 `log(1 + vip_level)`：** VIP 是歷史累積的落後指標，直接用它加權等於讓殭屍大課長佔用梯度預算。14天消費金額直接反映近期行為意圖，更準確。

**為何不加時間衰減到 weight 函數裡：** 把「距上次課金天數」當獨立 feature 讓模型自己學活躍與非活躍的分裂點，比在 weight 裡硬編更乾淨、更可解釋、更容易 debug。

---

### 離線評估框架

**評估時才用 hard boundary**，訓練時不用：

| Tier | 關鍵指標 | 警戒條件 |
|------|----------|----------|
| 高 VIP（有消費記錄） | AUC、Precision@K | 要有顯著提升 |
| 中 VIP | AUC lift | 不能退化 |
| VIP 0（新用戶） | Recall、Long Watch | **掉超過 2% 視為實驗失敗** |

新用戶是長期留存的種子，任何讓新用戶指標顯著退化的 weight scheme 都必須立刻修正，不能用「大課長變現提升」來 justify。

---

### Phase 2 觸發條件（結果出來才討論）

| 觀察到的現象 | 下一步 |
|-------------|--------|
| Session 特徵 importance 顯著 | 評估獨立 intent score module |
| 環境特徵 importance 顯著 | 加更多直播間即時 feature |
| 7/14 天消費 importance >> 30/90 天 | 考慮 session-level spending predictor |
| 多 tier 出現交互 pattern | 才評估 MMoE |
| Phase 1 跑完四項指標全無顯著 delta | 問題在 objective function，重新討論 label 設計 |

---

### 第一個實驗（本週）

加入 7/14/30/90 天消費金額 + 距上次課金天數，weight 用 `log(1 + 近14天消費金額)`，跑完用 tier-sliced AUC 評估。Feature importance 報告要一起出。
