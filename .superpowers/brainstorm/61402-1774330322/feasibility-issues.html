Feasibility Check — 3 個需要解決的坑

統一 agent config 前必須面對的架構衝突

Issue 1: Global Models Table 不能直接刪掉

問題

我原本提議用 adapter + adapterConfig 完全取代 Chat 的 global models table（config.json → models）。 但調查發現：

  • 10 個 agent 用 claude = 10 份重複的 cmd/baseUrl/timeout → 改一個要改十個
  • model_tiers.thinking 目前靠 global models 查找 thinking model 的連線資訊
  • Ollama endpoints（/providers/ollama/models）讀 global config 的 baseUrl
  • Settings Models Tab 整個 UI 假設 global models 存在

建議方案：Hybrid（保留 global + 允許 per-agent override）

// agents/claude/config.json
{
  "adapter": "claude_local",      // 指向 adapter type
  "model": "claude",              // soft ref → global models（連線資訊）

  "adapterConfig": {              // 可選：override global model 設定
    "timeoutSec": 180,            // 這個 agent 特別慢，給多一點
    "maxTurnsPerRun": 20          // Cowork 專用設定
  },

  "model_tiers": {
    "default": "claude",          // ref → global
    "thinking": "claude-opus"     // ref → global
  }
}

// config.json → models（保留，作為 adapter 連線資訊的共用 defaults）
{
  "models": {
    "claude": { "cmd": ["claude", "--print"], "idle_timeout_seconds": 120, ... },
    "claude-opus": { "cmd": ["claude", "--print", "--model", "opus"], ... }
  }
}

Merge 優先級： agent.adapterConfig > global models > hardcoded defaults
全局改一次，所有 agent 都生效。個別 agent 可以 override。

Issue 2: Mth 的 companyId + UUID — 最大的架構衝突

問題

Mth 的整個架構都假設：

  • 每個 agent 有 UUID（不是名字），所有 FK、路徑、API 都用 UUID
  • 每個 agent 屬於一個 company（companyId FK 必填）
  • 指令路徑 = companies/{companyId}/agents/{agentId}/instructions/
  • 所有 route = /companies/:companyId/agents（company-scoped）
  • 沒有 file → DB sync 機制

我們要的：agents/{name}/ file-based，用名字不用 UUID，全局不分 company。

建議方案：File-first + DB sync bridge

  • Source of truth = agents/{name}/config.json（file-based）
  • Sync service：啟動時 + file change 時，掃描 agents/ → upsert 到 Mth DB
  • Name → UUID mapping：DB record 加一個 fileKey 欄位 = folder name，用這個做雙向對應
  • Single company：你目前是 local_trusted 單人用，用一個 default company 就好。未來 multi-tenant 再拆
  • 指令路徑：Mth 的 instructionsFilePath 直接指向 agents/{name}/AGENT.md
// Sync 流程
agents/claude/config.json  →  DB agents table
  ├── fileKey: "claude"         (新欄位，name-based lookup)
  ├── companyId: DEFAULT_CO     (固定 default company)
  ├── id: auto-gen UUID         (Mth 內部用)
  ├── adapterType: from config
  ├── adapterConfig: { instructionsFilePath: "agents/claude/AGENT.md", ...merge from config }
  └── runtimeConfig: { heartbeat: from config }

Issue 3: 兩邊的 Agent 概念不同 — Runtime Context 設計

問題

Chat Agent Mth Agent
執行方式 WS 連線中 real-time streaming Heartbeat job，背景執行
生命週期 session 期間存活 run 結束就結束
Context multi-agent 對話歷史 issue + workspace + instructions
輸出 text chunks via WS code changes + run logs
與人互動 即時對話 非同步（assign → run → review）

建議方案：一個身份，兩個 runtime context

agents/claude/
├── config.json       ← 統一 config（身份 + adapter + skills + cowork settings）
├── AGENT.md          ← 共用指令（Chat & Cowork 都讀）
├── IDENTITY.md       ← 人格
├── SOUL.md           ← 驅動力
├── MEMORY.md         ← 長期記憶
└── memory/           ← 每日記憶

Runtime state（不在 file 裡）:
├── Chat context      ← Python 管理（session WS、對話歷史、mode toggle）
└── Cowork context    ← Mth DB 管理（heartbeat runs、task sessions、budget spent）

Config = 靜態身份（file）。Runtime = 動態狀態（各自管理）。
Chat 不需要知道 agent 在 Cowork 花了多少錢。Cowork 不需要知道 agent 在 Chat 說了什麼。
但兩邊讀同一份 AGENT.md、同一份 config.json。

總結：3 個坑的解法

Issue 風險 解法 可行?
Global models 刪掉會破壞 UI + model_tiers + Ollama 保留 global models 做 defaults + per-agent override ✅ 低風險
companyId + UUID Mth 全架構假設 UUID + company-scoped File-first + sync bridge + fileKey 欄位 ⚠️ 中風險，需要寫 sync service
Runtime context Chat streaming vs Mth job 是完全不同的執行模型 一個身份 file，兩個 runtime context 各自管理 ✅ 自然分離
