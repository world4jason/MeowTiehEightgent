Backend Merge: Stakeholder Perspectives

PM / CEO / CTO — each role weighs in on the merge direction

PM — Product Manager

RECOMMENDATION

A) Node eats Python — but phased, not big bang

Users don't care which runtime serves their chat. They care that Chat agents can work on Cowork issues and that Settings is one unified place, not a Frankenstein of two backends.

Right now the biggest product gap is: a Chat agent can't check out an issue, can't read project context, can't file a bug. That's the killer feature — conversational project management. Merging backends is the prerequisite.

Risk I worry about: 6-week merge project where nothing ships. Need to keep shipping features during the merge. Phase it so each chunk delivers user-visible value.

Key Priorities

  • Chat + Cowork integration (agent works on issues)
  • Unified Settings (one source of truth for agents)
  • Keep shipping during merge — no feature freeze
  • Session history must survive the migration

Concerns

  • Big bang rewrite = long dark period with no releases
  • File-based history → DB migration could lose data
  • Two "agent" concepts need clear UX resolution

CEO — Founder / Visionary

RECOMMENDATION

A) Node eats Python — and think BIGGER

Why are we merging? Not for code cleanliness. Because the product vision demands it. The 10-star version of this product is: you chat with AI agents who autonomously manage your entire project — file issues, review PRs, deploy code, track costs, all from a conversation.

Python Chat is 2,600 lines of beautiful simplicity — multi-agent orchestration, streaming, memory. But it's hitting a ceiling. No DB means no real querying, no joins, no cost tracking. Node/Mth already has all of that: 58 tables, plugin system, adapter layer, budget enforcement.

The real question isn't "merge backends" — it's "what does Chat become when it has a database, a plugin system, and a job scheduler?" That's the product unlock. Don't think of this as retiring Python. Think of it as graduating Chat into a full platform.

Opportunities

  • Chat agents gain: issue checkout, PR review, cost tracking
  • Cowork agents gain: real-time multi-agent conversation
  • One auth system, one deployment, one monitoring stack
  • Plugin ecosystem can extend Chat (MCP-style tools)

What keeps me up at night

  • Losing Python Chat's simplicity — it "just works" today
  • Node/Mth codebase is 10x larger — complexity risk
  • If merge takes too long, competitors ship first

CTO — Technical Architect

RECOMMENDATION

A) Node eats Python — with a strangler fig pattern

Option B (Python eats Node) is a non-starter. You'd be reimplementing 58 DB tables, Drizzle ORM, plugin system, adapter layer, and auth — in Python. That's 6+ months of rewrite with zero new features.

Option C (gateway) is a trap. You still maintain two backends, two deploy targets, two sets of bugs. The gateway adds latency and a third failure point. It delays the real work.

Strangler fig approach: Keep Python running. Build Chat features in Node one by one. Each phase, the UI switches one more endpoint from chatClient → api. When the last endpoint migrates, Python dies naturally. Zero big-bang risk.

Key technical insight: Python's Chat engine (conversation_engine.py, 200 lines) is the crown jewel — multi-agent turn scheduling, mention handling, probabilistic silence. Port this to TypeScript as a clean module. The rest (file I/O, CRUD routes) is mechanical migration.

Architecture Wins

  • PostgreSQL replaces fragile file-based storage
  • Drizzle ORM gives type-safe queries (vs raw JSON.parse)
  • Existing adapter system handles LLM providers properly
  • Heartbeat scheduler can replace Python's asyncio subprocess management
  • One WebSocket system instead of two

Technical Risks & Mitigations

  • History migration: file→DB is lossy if not careful. Write migration script + validation early
  • WS protocol: Python WS is simpler (direct stream). Node WS is event-based. Need adapter layer
  • Two "agent" concepts: Python agent = chat persona. Node agent = autonomous worker. Must coexist, not merge prematurely
  • conversation_engine.py: Port carefully — async Python → async TypeScript has subtle timing differences

Consensus: A) Node eats Python

All three roles agree on direction. The debate is on execution strategy:

  • PM: Phase it — each chunk ships user value, no feature freeze
  • CEO: Think platform — Chat graduating into a full-stack product, not just a port
  • CTO: Strangler fig — migrate endpoint by endpoint, Python dies naturally when empty
